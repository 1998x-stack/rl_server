## 1. 一句话总结

这次不是加功能，而是**先把"看不见"变成"看得见"，再修被看见的真问题**：

1. 日志系统此前既过载又缺失——worker 日志全部丢失，关闭流程会无限重入，所以没人发现 SAC 根本没训练、MicroRTS 全是 NaN 梯度、DQN 每次更新都在重置 Adam。
2. 修完可观测性后，逐个环境实测（7 个 registry key）修掉训练正确性问题。
3. 最后把"看得见"固化成流水线：隔离检查运行器 + 独立评测器（含真实 LLM judge），并接进 CI。

## 4. 必须知道的不变量（不遵守会静默破坏可观测性）

1. **`Log` 必须经 pickle 传给 worker**（或 worker 内重新构造）。spawn 子进程不继承 handler，`Log.__setstate__` 会在子进程重建并写 `<dir>.<pid>.log`。**不要在子进程里 `logging.getLogger(...).info(...)` 直连标准库**——没有 handler，日志直接消失。
2. **只有 `trainable_parameters(net)` 能进梯度聚合**。SAC 的目标 critic 是 `requires_grad=False` 的参数，混进 `parameters()` 会让 `len(grads) != len(params)`，整批被拒（表现为"训练不动"）。
3. **优化器必须复用**（`get_cached_adam`）。每次 `update_state` 新建 Adam 会把一阶/二阶矩清零。
4. **写梯度用 `assign_gradients`**。`torch.FloatTensor(grad)` 在 0 维参数（`log_alpha`）上抛 `TypeError`。
5. **关闭流程只跑一次**。任何"在热循环里做关闭 + 宽泛 except"的写法都会变成无限重入（原 bug 复现了 6.5 万次）。关闭步骤一律放进 `_run_shutdown(steps, log)`，每步独立兜底。
6. **阻塞调用必须有超时**（`Queue.put(timeout=)` / `Queue.get(timeout=)`）。否则 worker 看不到 `is_exit`，只能被强杀，env/JVM 不清理且会泄漏 semaphore。
7. **每个 e2e 环境必须独立 artifact 目录**。共用一个 `RL_SERVER_LOG_ROOT` 会让后一个环境的日志追加到前一个后面，评测读到别人的指标（真实发生过）。

## 5. 运行方式速查

```bash

# 分布式（需要 Redis；host 与 port 都支持环境变量）

# 检查 + 独立评测（一条命令）

  python scripts/run_checks.py all --seconds 16 --evaluate --update-baseline
```

## 6. 新增配置项（`rl_server/config/default.yaml`）

| 键 | 默认 | 含义 |
|---|---|---|
| `training.max_gradient_lag` | `auto` | 允许的梯度滞后；`auto` 按实测 p95 到达滞后自适应；整数固定；`0` 严格同步（并发下会丢在途批次） |
| `training.max_gradient_lag_cap` | `64` | `auto` 的上限 |
| `training.version_log_interval` | `10` | 每 N 个版本一行进度（第 1 版永远输出） |
| `training.cold_start_versions` | `20` | 前 N 版的拒绝单列 `cold_start_rejected`，不污染稳态拒绝率 |
| `training.stall_warn_secs` | `60` | 多久没有梯度被接受开始告警 |
| `training.stall_fatal_secs` | `300` | 多久后中止（退出码 1） |
| `training.check_log_interval` | `100` | checker 每 N 次评估输出一行 |
| `logging.throttle_secs` | `60` | 重复消息最小输出间隔 |

环境变量：`RL_SERVER_LOG_ROOT`、`RL_SERVER_MODEL_DIR`、`RL_SERVER_TENSORBOARD_DIR`（隔离用）、`REDIS_*_HOST` / `REDIS_*_PORT`、`RL_RUN_ID`、`RL_JUDGE_CMD` / `RL_JUDGE_CLI` / `RL_JUDGE_API_BASE` / `RL_JUDGE_MODEL` / `RL_JUDGE_API_KEY`。

## 7. 调试手册（症状 → 去哪看 → 常见根因）

| 症状 | 先看 | 常见根因 |
|---|---|---|
| 训练"在跑"但版本不涨 | 进度行 `accepted/rejected/cold_start_rejected`；是否有 `aborting: no gradient applied` | 算法产不出可用梯度（`reason=none_gradient`）→ 看 `hint=`；worker 全死会直接 exit 1 |
| 版本涨但 loss 不降 | 进度行的 `q_loss/policy_loss/entropy`；TensorBoard（启动行给了绝对路径） | 优化器被重置、奖励未截断（Atari）、学习率过大 |
| 梯度拒绝率高 | `gradient rejection rate high ... reject_pct= reason= hint=` | `stale_version` → 吞吐配比（加 trainer / 调 `num_update_grads`）；`non_finite` → 看 loss 是否发散 |
| 日志里没有任何指标 | 是否版本数 < `version_log_interval` | 已由"第 1 版必出进度行"覆盖；若仍无，检查 `trainer_metrics` 是否被算法写入 |
| worker 莫名消失 | 主日志 `worker died ... exitcode=`；子日志 `train_main_local.<pid>.log` | 缺依赖（如 `cv2`/`ale_py`）、JVM 未授权、算法初始化异常 |
| 关闭很慢 / 卡死 | `shutdown step=<name> took=`、`stopped ... graceful= exitcode=` | rollout/评估不可中断（已加 `is_exit`/`should_stop` 检查）；Redis BRPOP 5s 上限 |
| Redis 相关卡住 | `pop_exps empty/pop_grads empty ... queue_len=`、`Redis write recovered/op=` | 生产>消费、连接抖动；两者现在都与"没数据"区分开了 |
| CI 与本地结果不一致 | `.checks/<id>/eval/report.md`、`typecheck/mypy.log` | 机器指纹不同（吞吐已按机器隔离）、工具版本漂移（CI 已 pin） |

## 8. 检查与评测管线（细节见 `docs/checks.md`）

- **判定三级**：`pass` / `warn` / `fail`。`warn` 不失败但会进报告与裁判证据；`--strict-warn` 可升级。
- **评测器不信任运行器**：自己从原始日志重算版本数、拒绝直方图、worker 退出码、指标趋势、行/版本密度，并比对"运行器报的数字 == 重算的数字"。
- **回归基线** `eval/baseline.json`：含 `host` 指纹，跨机器不比较绝对吞吐；吞吐基线"只升不降"。
- **LLM judge**：`scripts/judge_pi.sh`（默认 `pi -p`）→ 严格 JSON 判决；`verdict: fail` 会让整体失败、`warn` 降级为 warn；无后端时 `skipped`（显式，不伪装通过）。
- **CI**：`.github/workflows/python-regression.yml` 在单测之后跑 `run_checks.py unit lint typecheck e2e --envs DQNGymClassic`，再跑 `evaluate.py`，并上传 `.checks/` artifact；工具版本已 pin（`ruff==0.17.3`、`mypy==2.4.1`）。

## 9. 待决项 / 后续建议（不是缺陷，需要产品决策）

1. **`sample_lag` 的上限**：DQN 里 `sample_lag` 会从 10 涨到 ~107（每批样本被复用 ~10 个版本）。这是当前架构（`num_update_grads=1`）的固有特性，评测器暂以 `≤200 且 ≤20×first` 作为 warn/fail 边界。若希望更"新鲜"，应改为 `num_update_grads>1` 或按 `sample_version` 分组更新。
2. **SAC 吞吐配比**：`reject_pct≈30–38%` 源于 trainer 出梯度快于主循环应用，属容量问题。选项：加 `num_trainers`、调 `num_update_grads`、或让主循环按 `grads_version` 分组累加（会改变更新语义，需评审）。
3. **SAC 优化器拆分**：目前 policy/critic/alpha 在同一个 `update_state` 内分组 step。标准实现用独立 optimizer + 独立调度，属语义升级。
4. **MujocoBeta 熵口径**：Beta 策略的 entropy 量级（~0.015）与 PPO Normal 不同，评测器的熵阈值目前统一，建议按算法区分。
5. **Atari 裁剪饱和**：修复奖励截断+Huber 后 `grad_scale` 从 2.5e6 降到 ~1.5e3 并继续下降，但 `clip_frac=1.0`。是否把 `MAX_GRAD_NORM` 提到 ~100 或降学习率，需要看更长训练曲线的稳定性。
6. **CI 里的 judge**：目前 `judge: skipped`（runner 无后端）。若要启用，在 Secrets 配 `RL_JUDGE_API_BASE` / `RL_JUDGE_MODEL` / `RL_JUDGE_API_KEY` 并在 workflow 注入这三个 env。
7. **趋势断言的稳健性**：现在是"首末两点 + 固定倍数"。可升级为窗口分位数 / 斜率 + 连续两次回归才判失败，减少长短跑差异带来的抖动。

- import 侧新增依赖：`rl_server.core.optim`、`rl_server.core.gradient_contract`（纯内部，无第三方新依赖）。
